# 作業ステータスの置き場所ルール

作業は Mac（`local-workspace`）と Windows/WSL（`local-workspace-win`）のどちらからでも再開しうる。
auto memory（`~/.claude/projects/.../memory/`）と local-workspace はそれぞれ **その PC にしか無い**。
ここにしか書かれていない情報は、もう一方の PC で作業を再開したときに失われる。

## 原則

**作業対象のリポジトリがはっきりしているなら、詳しい作業ステータスはそのリポジトリに書く。**
local-workspace 側（memory・バックログ）は「どこで何をしているか」がわかる索引にとどめる。

| 置き場所 | 書くこと |
| --- | --- |
| 対象リポジトリの `docs/STATUS.md` | 現在地・次のアクション・決定事項とその理由・検証済みの技術知見・保留事項・PC ごとの環境差 |
| local-workspace の memory / バックログ | 1件1〜2行。リポジトリのパス、ひとことで言う現状、「詳細は `<repo>/docs/STATUS.md`」 |

- リポジトリにすでに決まった置き場所があればそちらを使う（例: podcast-copilot の
  `shows/<番組>/show.md`、スキルの手順なら SKILL.md）。無ければ `docs/STATUS.md` を作る。
- 対象リポジトリが無い作業（調べもの、単発の相談、ハーネスそのものの話）は従来どおり
  memory に書いてよい。

## STATUS.md の形

```markdown
# 作業ステータス

最終更新: YYYY-MM-DD（Mac / WSL）

## 現在地
進行中のブランチ・PR、本番に出ているバージョン

## 次のアクション
1. ...

## 決定事項
- 何を決めたか ― なぜそうしたか（ユーザーが決めたものはそう書く）

## 技術知見（検証済み）
- 再び踏みそうな罠と回避策

## 保留・未確認
- 誰の返事待ちか、何がまだ確かめられていないか

## 環境メモ
- 片方の PC にしか無いもの（.env、clasp/gcloud のログイン、ローカルのファイル）
```

日付は相対表記（「昨日」「来週」）にせず絶対日付で書く。

## いつ書くか

- **作業を始めるとき**: `git fetch` してから STATUS.md を読む。もう一方の PC で進んでいる可能性がある。
- **区切りのとき**: PR を作った・マージした・デプロイした・方針が決まった、など。
- **セッションを終える前 / PC を移る前**: 必ず更新し、**commit して push する**。
  push していない STATUS.md は、もう一方の PC からは見えない。
- コミットは作業ブランチに含めてよい（PR と一緒にマージされる）。main 直 push 禁止のルールは
  STATUS.md の更新でも変わらない。未マージのブランチにしかない場合は、memory の索引に
  ブランチ名を書いておく。

## 書いてはいけないもの

- 秘密情報（トークン、パスワード、API キー、`.env` の中身）。ID 類は「秘密でなければ」可。
- **公開リポジトリ**では、個人名・社内事情・未公開の予定も書かない。迷ったら
  `gh repo view --json visibility` で確かめ、公開なら memory 側に残してユーザーに確認する。

## memory との分担

- memory に詳細を書きかけたら、それはリポジトリへ移す内容ではないかを疑う。
- 古い memory に詳細が残っているのを見つけたら、リポジトリの STATUS.md へ移し、
  memory は索引の1行に縮める（移したことはユーザーに一言伝える）。
