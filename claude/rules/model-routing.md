# モデルルーティング & サブエージェント委譲ルール

トークン（＝レート制限枠）効率と、判断品質の両方を守るためのルール。

## 判断は2軸で行う（1軸にしない）

委譲の是非を「タスクの大きさ」だけで決めない。次の2軸を独立に評価する。

- **コンテキスト移送コスト**: サブエージェントは fresh context で起動する。いま main が
  持っている情報を、どれだけ読み直させる必要があるか。
- **必要な推論能力**: そのタスクを、いまのセッションモデルで正しく解き切れるか。

**「指示が短いから委譲しない」は誤り。** 委譲オーバーヘッド論が効くのは *大量のファイルを
読み直させる* タスクであって、*考える量が多い* タスクではない。設計判断や原因究明は
指示が3行でも難易度は高く、しかも問題を数段落で説明できる＝移送コストは小さい。
このゾーンこそ委譲の費用対効果が最も高い。

|                  | 移送コスト小                          | 移送コスト大                                          |
| ---------------- | ------------------------------------- | ----------------------------------------------------- |
| **通常の難易度** | main で直接やる（委譲しない）         | explorer(haiku) に下調べだけ投げ、結論を受けて main で実装 |
| **高難易度**     | **strategist(fable) に委譲**          | explorer で材料を集めて要約 → その要約を strategist に渡す |

## 昇格トリガー（当てはまれば確認を取らずに strategist へ委譲する）

- アーキテクチャ・技術選定・データモデルなど、**後戻りコストが高い設計判断**
- 再現条件が不明、または直したつもりで再発しているバグの**根本原因調査**
- 複数案のトレードオフを比較して1つに決める必要がある
- 1セッションに収まらない規模の移行・リファクタの**計画立案**
- **同じ失敗を2回繰り返した**とき（打ち手ではなくアプローチ自体が疑わしい）

委譲時は、main が既に把握している事実（読んだファイル、試した手、エラーの実物）を
依頼文に書き下ろす。strategist に同じ調査をやり直させないこと。

## 昇格しない（main のまま進める）

- 実装方針が既に決まっていて、あとは書くだけ
- 事実確認・場所探し（explorer で足りる）
- 機械的作業（mechanic で足りる）
- ユーザーが既に方針を指定している（勝手に設計を蒸し返さない）

## エージェント一覧

| タスク                                             | エージェント | モデル       |
| -------------------------------------------------- | ------------ | ------------ |
| 設計判断・根本原因調査・大規模計画（上記トリガー） | `strategist` | fable        |
| コードレビュー・セキュリティレビュー               | `reviewer`   | 継承（Opus） |
| 広域コード探索・長いログや大量ファイルの要約       | `explorer`   | haiku        |
| rename・一括置換・テスト実行と結果報告・lint 修正  | `mechanic`   | haiku        |
| 独立した並列調査（互いに依存しない複数トピック）   | 並列で複数   | 内容に応じて |

> 注意: 組み込み Explore エージェントは v2.1.198 以降メインセッションのモデルを継承するため、
> トークン節約目的の探索委譲には使わない。必ず `explorer`（haiku）を使うこと。

## 委譲後の運用

委譲するかどうかとは別に、委譲した「あと」の扱い方で差が出る。

- **並列は2〜4体を目安にする。** 5体以上必要になったら、投げ方が悪いサインとして
  タスクの粒度と結果の集約方法を見直す（並列数を増やして押し切らない）。
- **サブエージェントはスキルを継承しない。** 呼び出し元でスキルを実行中でも、その内容は
  サブエージェントに渡らない。スキルの手順に従わせたいなら、該当部分を依頼文に書き下ろすこと。
  エージェント定義の `skills` フロントマターで明示的に持たせる手もある。
- **完了待ちのポーリングをしない。** 結果取得ツールを待機目的で繰り返し呼ぶと、生の
  トランスクリプトが返って呼び出し元の context を圧迫する。完了はイベント通知で受け取る。

## モデル選択

- **main セッション**: `settings.json` に `model` キーを**置かない**ことで推奨モデルに追随する。
  特定バージョンを pin しないので、推奨が更新されれば自動で乗り換わる。
  `"model": "default"` と書いてはいけない。`default` が「指定解除」として通るのは `/model`
  コマンド・`--model` フラグ・`fallbackModel` の要素だけで、`model` キーでは未知のモデル名
  として扱われ、context window を 200k と誤認して auto-compact が早期に走る。
- **fable**: `strategist` 経由でのみ使う。最も難しく、最も長い仕事向け。
  Fable は手順ではなく「欲しい結果」を渡すと力を発揮する（自分で調べて自分で検証する）。
  Fable の安全分類器に弾かれた場合のフォールバックは `settings.json` の `fallbackModel`
  で決定論的に設定済み。
- **haiku**: explorer / mechanic。機械的・定型作業はこれで十分。

セッション途中の `/model` 切替は prompt cache を破棄するため、長い会話の途中では割高。
単発の難所は切替ではなく `strategist` への委譲で処理する。

## advisor tool を採用しない理由（将来の再検討メモ）

Claude Code には advisor tool（判断点で第二のモデルに全会話を読ませて助言させる機能、
`advisorModel` 設定）がある。ただし現時点では **Fable を advisor に選べない**
（`/advisor` で "Fable 5 (temporarily unavailable)" として無効表示、`--advisor fable` も拒否）。
main が Opus の場合 advisor も Opus 止まりで「より強いモデルへの昇格」にならず、
トークンだけ増えるため見送る。ロールアウトで Fable が advisor に開放されたら
`"advisorModel": "fable"` を再検討する。

## その他の効率ルール

- 長いセッションでは区切りのよいところで `/compact` を検討
- 不要な MCP サーバー・プラグインは有効化しない（context を常時圧迫するため）
