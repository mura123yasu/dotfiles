# 私の Claude Code 活用方法

設定を「たまに触るもの」から「git で管理し、PR で変える資産」に格上げすると、
AI コーディングは道具から作業環境になる。本書はその環境の設計図
——どのモデルに何を任せ、どこで止め、どうやって陳腐化を防ぐか。

- 前提: Claude Max サブスクリプション / macOS + WSL
- 実体: `dotfiles`（配布される設定）と `local-workspace`（進捗と自動化の司令塔）の2リポジトリ
- 本書は要約。個別の正本は `claude/rules/model-routing.md`・`CLAUDE.md`・`harness/README.md`

> 更新方針: ハーネスを変えたら本書も同じ PR で更新する。実装と説明が乖離した時点で価値を失うため。

---

## 出発点: サブスクにおける「コスト」はお金ではなく、レート制限枠

API 課金前提で書かれたトークン節約術は、そのままでは当てはまらない。
定額プランで減るのは残高ではなく **5時間ウィンドウの残枠**で、枠を使い切った瞬間に作業が止まる。
つまり節約の目的は請求額ではなく **「止まらないこと」** になる。
この読み替えが、以下すべての判断の土台になっている。

もうひとつの土台は context。MCP サーバーやプラグインを盛ると常時ロードで実効 context が数分の一に縮む。
使うものだけを有効にし、恒常ルールは `CLAUDE.md` ではなく `~/.claude/rules/` に置いて薄く保つ。

## 5つの考え方

### 1. 委譲の判断を「タスクの大きさ」1軸でやらない

評価するのは **コンテキスト移送コスト**（サブエージェントは fresh context で起動する。何を読み直させるか）と
**必要な推論能力**（今のモデルで解き切れるか）の2つ。
「指示が3行だから自分でやる」は誤り——設計判断は指示が短くても難しく、しかも数段落で説明できる。

### 2. モデルも effort も「役割ごとに宣言する」

全ターンを最高設定に固定するのは、**一番難しい1ターンに全ターンを合わせる**こと。
モデルだけ振り分けて effort を固定するのも片手落ち。役割の定義ファイルに、モデルと effort を並べて書く。

### 3. ガードレールは一枚の網に頼らない

permission の deny ルールは**プレフィックス文字列マッチ**なので `rm -fr` や `/bin/rm` のような変種で抜ける。
抜ける前提で、分類器・宣言的ルール・regex hook・サンドボックスを重ねる。

### 4. ハーネス自体をリポジトリに置き、PR で変える

`~/.claude` 配下は dotfiles からの symlink。設定変更もレビュー対象で、履歴が残り、別マシンへ配れる。
設定をローカルで直接編集すると、なぜそうしたかが半年後に失われる。

### 5. 陳腐化を運用でなく仕組みで防ぐ

Claude Code は週単位で変わる。追従を気合いに任せず、
**調査 → 起案 → 人間の採否判断 → 実装 → 記録** のサイクルをスキルとして常設し、月1〜2回まわす。

## 構成: 2つのリポジトリに役割を分ける

「配布される設定の実体」と「進捗と自動化の司令塔」を混ぜない。
前者を別マシンへ配っても、後者のタスク管理は持ち込まれない。

| リポジトリ | 役割 | 中身 |
| ---------- | ---- | ---- |
| `dotfiles` | 配布される設定の実体。`install.sh` が `~/.claude` へ symlink を張る | `claude/settings.json` / `agents/` / `hooks/` / `rules/` / `skills/` / `CLAUDE.md` |
| `local-workspace` | 全リポジトリ横断の司令塔。ここで Claude を起動して「次何やる？」を聞く | `BACKLOG.md` / `projects/` / `automation/` / `.claude/skills/` |

## ルーティング: どこに投げるかを2軸で決める

|                  | 移送コスト 小 | 移送コスト 大 |
| ---------------- | ------------- | ------------- |
| **通常の難易度** | **main セッションで直接**（委譲しない。読み直しのオーバーヘッドが利得を食う） | **explorer → main**（下調べだけ軽量モデルに投げ、結論だけ受け取って実装は main で） |
| **高難易度**     | **strategist（最上位モデル）**。最も費用対効果が高いゾーン。問題は数段落で説明でき、判断ミスの代償は大きい | **explorer → strategist**（材料集めと要約を挟んでから、その要約を渡す） |

### 確認を取らずに最上位モデルへ上げる条件

「上げますか？」と聞くこと自体がターンの浪費なので、以下は無断で昇格させる約束にしてある。

- アーキテクチャ・技術選定・データモデルなど**後戻りコストが高い設計判断**
- 再現条件が不明、または直したつもりで再発しているバグの**根本原因調査**
- 複数案のトレードオフを比較して1つに決める必要がある
- 1セッションに収まらない規模の移行・リファクタの**計画立案**
- **同じ失敗を2回繰り返した**とき（打ち手ではなくアプローチ自体が疑わしい）

### エージェント

| 担当 | 役割 | モデル | effort |
| ---- | ---- | ------ | ------ |
| `strategist` | 設計判断・根本原因調査・大規模計画。読み取り専用で、実装は main に戻す | 最上位 | `max` |
| `reviewer` | コードレビュー・セキュリティレビュー。指摘のみ、修正しない | セッション継承 | `xhigh` |
| `explorer` | 広域探索・長いログの読解と要約。結論と `path:line` だけ返す | haiku | `low` |
| `mechanic` | rename・一括置換・テスト実行・lint 修正 | haiku | `low` |
| `harness-researcher` | ハーネス改善のための Web 調査 | sonnet | 継承 |

### 委譲した「あと」で差がつく3点

- **並列は2〜4体まで。** 5体以上必要になったら、投げ方が悪いサインとしてタスクの粒度を見直す（並列数で押し切らない）。
- **サブエージェントはスキルを継承しない。** 呼び出し元でスキルを実行中でも中身は渡らないので、従わせたい手順は依頼文に書き下ろす。
- **完了待ちのポーリングをしない。** 結果取得ツールを待機目的で叩くと生のトランスクリプトが返り、呼び出し元の context を圧迫する。

## 防御: 4層で止める

層が下にいくほど「宣言的で読みやすいが穴がある」から「読みにくいが確実」へ移る。
上の層をすり抜けたものを下の層が拾う前提で組む。

| 層 | 内容 | 場所 |
| -- | ---- | ---- |
| 1 | **auto permission mode（組み込み分類器）**。force push・`curl \| bash`・本番デプロイ等を既定でブロック。手製の YOLO ガードより、これを土台にする | `settings.json` |
| 2 | **deny / ask ルール**。deny に破壊系コマンドと機密ファイル読み取り、ask に `gh pr merge`・`launchctl`。宣言的で読みやすいが、プレフィックスマッチゆえ変種で抜ける | `settings.json` |
| 3 | **ネイティブサンドボックス**。全セッションに常時適用。書き込み可能パスと egress ドメインを allowlist で絞る。自動実行時はさらに Docker で二重化 | `settings.json` |
| 4 | **PreToolUse hook — 最後の砦**。Bash コマンドを regex 検査して deny を返す。`rm -fr` のような変種、`main` への直接 push、Keychain 読み出しなどを捕捉。**この deny は権限スキップ下でも headless 実行でも有効**——だから自動実行の安全性はここに預けている | `claude/hooks/guard.sh` |

同じ思想がワークフローにも入っている。**main への直接 commit・push は禁止**で、
これはグローバルルールに書いた「お願い」であると同時に、hook による**決定論的な強制**でもある。
文章のルールは忘れられうるが、hook は忘れない。

## 運用: 1日の流れはスキルで固定する

毎回プロンプトを書き起こす作業は、書き起こすたびに手順がブレる。
定型はスキル（スラッシュコマンド）に落として、入口だけ覚えておく。

| スキル | 用途 |
| ------ | ---- |
| `/next` | バックログ・各リポの進捗ファイル・実際の PR 状態を突き合わせ、「今それをやる理由」付きで1〜3件提案させる。最優先は自分にしかできないこと（レビュー・判断待ち） |
| `/add-task` | バックログに積む。`auto:yes` を付けた小タスクは自動実行キューにも入る |
| `reviewer` / `/code-review` | 自分の目の前に、指摘専用の読み取り専用エージェントを1枚挟む |
| `/github-push` | 変更種別からブランチ名の接頭辞を決め、ブランチ作成 → commit → push → PR 作成までを1メッセージで |
| `/sync-status` | 週1。進捗ファイルの記載と実際のコミット・PR・CI の差分を検出して直す |
| `/dotfiles-drift-check` | 実環境とリポジトリのドリフトを検出し、必要なら追従の PR を出す（自 OS のファイルだけ触る制約付き） |

### 定期実行スキルと、スケジュール組み込み状況

スキルには**イベント駆動**（やりたい時に叩く）と**定期実行**（叩き忘れると静かに腐る）の2種類がある。
後者を人間の記憶に依存させないのが目標。現状は以下（2026-08-09 時点）。

| スキル | 定義元 | 想定頻度 | 組み込み | 実体 |
| ------ | ------ | -------- | -------- | ---- |
| `/dotfiles-drift-check` | dotfiles | 週1 | **検出のみ済** | `.zshrc` 起動フックが週1で `scripts/drift-check.sh --quiet` をバックグラウンド実行し、差分があればシェル起動時に警告。分類・修正・PR を行うスキル本体は人間が起動する |
| `/harness-improve` | dotfiles | 月1〜2 | **未** | 完全手動。頻度が低いぶん最も忘れやすい |
| `/sync-status` | local-workspace | 週1 | **未** | 完全手動 |
| `/standup` | local-workspace | 週1 | **未** | 完全手動 |
| `/next` | local-workspace | 作業開始時 | 対象外 | 定期実行しない。自分が動き出すときに叩くもの |
| `/add-task` | local-workspace | 随時 | 対象外 | イベント駆動 |
| `/github-push` | dotfiles | 随時 | 対象外 | イベント駆動 |

スキル以外の定期実行の仕組み:

| 仕組み | 間隔 | 状態 |
| ------ | ---- | ---- |
| `.zshrc` のドリフト検出フック | 週1（シェル起動時に経過判定） | **稼働中**（Mac / WSL 両方） |
| `automation/com.mura123yasu.claude-autorun.plist`（usage-watch → 自動実行） | 30分 | **未登録**。`~/Library/LaunchAgents/` に置かれておらず、キュー処理基盤ごと停止中 |
| cron / Claude Code Routines（`/schedule`） | — | **未使用**（`crontab` 空、`~/.claude/scheduled_tasks.json` なし） |

> 注記: 定期実行を仕込むだけでは足りず、**出力が信用できる状態を保つ**必要がある。
> 現に週1のドリフト検出は、Brewfile に記載済みのパッケージまで「未記載」として並べており（`brew bundle dump` の
> 出力形式との比較ずれ）、警告に対する感度が下がっている。ノイズを出す定期実行は、無い場合より悪い。

### スケジュール組み込みが推奨されるもの

判断基準は2つ。**忘れると静かに腐るか**（実行間隔が長いものほど忘れる）と、
**人間の判断を挟まずに完了できるか**。後者を満たさないものは最後まで自動化せず、
**「人間が判断できる状態まで運んでおく」**ところで切る。

| 優先 | 対象 | 理由と、どこで切るか |
| ---- | ---- | -------------------- |
| 1 | **`/harness-improve` の調査・立案フェーズ** | 月次＝最も忘れやすく、放置するとハーネス全体が古びる。採否判断は人間の仕事なので、**`harness/proposals/` への起案 PR を出すところまで**を自動化し、人間はレビューから入る |
| 2 | **`/sync-status`** | 週次。やり忘れると進捗ファイルが実態から乖離し、`/next` の提案精度がそのまま落ちる。スキル本文が「diff を示してから適用」を求めているので、**PR 止まり**にする |
| 3 | **`/standup`** | 週次・副作用ゼロ（読むだけ）。月曜朝に届くなら有用だが、読む習慣がなければ通知が増えるだけ。任意 |
| 前提 | **自動実行 launchd の登録** | 上のどれをローカルで回すにも土台になる。未登録のままだと `automation/` 一式が資産として遊んでいる |

`/dotfiles-drift-check` の**対処フェーズは自動化しない**。パッケージ差分の採否は判断を要し、
かつ「変更するのは実行端末の OS 用ファイルだけ」という制約があるため、検出（済）と警告で止めるのが正しい。

実装手段は2択で、既存資産が効くのは後者:

- **Claude Code Routines（`/schedule`）** — クラウド実行。Mac の電源状態に依存しない。反面、ローカルのガードレール（`guard.sh` / サンドボックス）の外側で動く
- **launchd + `claude -p`（既存の `automation/` 基盤）** — ローカル実行。Docker サンドボックス・ブランチ+PR 強制・allowlist・サイズ制限の四点セットをそのまま継承でき、「枠が余っている時だけ動く」判定も既にある。定期タスクを `automation/queue/` へ流し込む形にすれば追加実装が小さい

### 人間不在時の自動実行（枠が余っているときだけ動く）

30分ごとに使用量を見て、**キューにタスクがあり・実行中がなく・対話セッションが動いておらず・
5時間ウィンドウの使用率が50%未満で・残り60分以上** ——すべて成立したときだけ、1件だけディスパッチする。
実行は Docker 内の headless セッションで、対象リポジトリだけを mount し、
認証情報はファイルではなく環境変数で注入する。
成果は必ず PR として上がり、**マージ判断は人間に残る**。自動化するのは作業であって、承認ではない。

## 保守: ハーネス自身を改善するサイクルを常設する

月1〜2回 `/harness-improve` を回す。調査は専用エージェントに2並列で任せ、
**main セッションでは Web 調査をしない**（context 汚染を避ける）。

1. **調査** — 前回の確認範囲以降の CHANGELOG・公式ドキュメント・コミュニティ知見だけを差分で読む
2. **立案** — 現状と突き合わせて `harness/proposals/` に起案する
3. **レビュー** — 採用 / 却下 / 保留は人間が決める。**勝手に実装させない**
4. **実装** — 採用分だけを反映し、PR にする
5. **記録** — `harness/research-log.md` に確認範囲を残し、次回は差分だけ調べる

提案ファイルは却下・実装済みも**削除せず残す**。`status: rejected` と理由が残っていれば、
半年後に同じ案が再提案されても即座に判断できる。
あわせて、スキル実行中に踏んだ詰まりはそのスキルの末尾「Gotchas」に1行だけ追記して同じ PR に含める
——失敗が次の実行の前提になる。

## 実測: 実際に踏んで直した思い込み

どれも「もっともらしいが間違い」だったもの。裏を取らずに設定を書くと、静かに損をする。

| ✗ 思い込み | 実際 |
| ---------- | ---- |
| モデル指定を外すには `"model": "default"` と書く | `default` が「指定解除」として通るのは `/model`・`--model`・`fallbackModel` の要素だけ。`model` キーでは未知のモデル名として扱われ、context window を 200k と誤認して auto-compact が早期に走る。**キー自体を置かない**のが正解 |
| 軽量モデルに高い effort を払っていて無駄 | haiku はそもそも effort 非対応。無駄は発生していなかった。削減効果が出るのは main セッション側。**issue に書いた前提のほうが間違っていた**ケース |
| 設定ファイルに最高 effort を書けば常に全力になる | `effortLevel` が受け付けるのは `low` / `medium` / `high` / `xhigh` の4つ。`max` はセッション限りの値で恒久設定には書けない。エージェントの frontmatter でなら指定できる |
| effort は最高にしておけば安全 | 公式ドキュメントに「難しいタスクで改善しうるが**収穫逓減があり overthinking しやすい**」とある。だから `max` は `strategist` 1体に限定している。単発の難所は設定を上げるより、プロンプトに `ultrathink` を含めるほうが安い |
| fallback 先を最新の最上位モデルに固定すれば安心 | 主モデルが同じものになった瞬間、逃げ先として機能しなくなる。**エイリアス指定にして世代に追随させる** |
| API が 404 なら main ブランチは保護されていない | ruleset で保護している場合、旧 `branches/*/protection` API は 404 を返す。確認先を間違えると「無防備」と誤診する（確認は `rulesets` API を使う） |

## 始め方: 真似するなら、この順番

全部を一度に作る必要はない。効きが早い順に並べるとこうなる。

1. **設定を git に入れて symlink 配布にする。** ここを済ませないと、以降の改善が積み上がらない
2. **禁止事項を deny ルールと PreToolUse hook の2枚で書く。** 特に main への直接 push。文章のルールだけでは守られない
3. **役割ごとのエージェントを3体だけ作る。** 探索（軽量モデル）・レビュー（継承）・設計判断（最上位）。多く作るより、いつ呼ぶかの基準を書くほうが効く
4. **毎回書いているプロンプトをスキルにする。** PR 作成、進捗確認あたりが最初の候補
5. **追従サイクルを常設する。** ここまで作った資産は、放っておくと半年で古びる
